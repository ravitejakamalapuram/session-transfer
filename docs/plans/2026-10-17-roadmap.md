### Decided 2026-10-05, reopened: encryption on by default

The owner agreed on 2026-10-05 (cross-device plan, step 1) that packages should be encrypted by default; it was never
built. Today `keyMode` defaults to `'none'` (`extension/src/core/crypto.ts`) and `requireCode` starts `false`
(`extension/src/popup/App.tsx`), because 1.3.0 (#21) chose plain packages so a move is one paste.

- **Why it matters:** a plain package is a working login. Pasted into chat, email or a ticket, anyone who sees it can use
  it until the cookies expire. This is the biggest security gain available, and it makes the live listing's
  "encrypted" wording true again.
- **What it costs:** every move gains one step (copy the package, then type or paste a short code on the other side),
  plus a copy rewrite of README, listing and in-popup text. Privacy policy wording stays with the owner. Effort S to M.
- **Recommended design:** encrypted by default, with a visible "Skip the code (same computer only)" switch on the send
  screen that remembers the choice. Receive accepts both, as today. Ship it in the same release as the fixes in
  "Now", so the store never carries a plain-by-default version with old "encrypted" copy.
- **Then step 2:** an admin kill switch through `chrome.storage.managed` and a `managed_schema`, so a company can turn
  export and import off. Effort S.

## Known risks (document, do not evade)

- Copying session cookies is what infostealers do. Corporate EDR or DLP tools may flag the extension whatever the
  transport. The listing says it is for your own accounts and QA.
- Chrome Device Bound Session Credentials bind some sessions to one device by design, so those sessions will fail on a
  second computer. Report it as a known limit, never work around it.
- Marketing targets QA engineers and testers only (decided 2026-10-05).

## Not worth it (decided, do not reopen without new evidence)

- **Cloud sync or accounts.** Contradicts the local-only promise that is the product's trust advantage, and adds a
  server to secure and pay for.
- **General cookie editor.** Cookie-Editor owns that market; it dilutes the "move a whole session" position.
- **Chasing the Featured badge.** Google is not taking requests and the criteria are not published.
- **QR pairing and a one-time-code relay** (old README roadmap, deleted `memory/PRD.md`). Superseded by the WebRTC plan.
- **Command-line helper for Playwright `storageState`** (`GROWTH_PLAN.md` section 7). The popup already exports
  `storageState` since 1.4.0.
- **Field-level merge** (old README roadmap, PRD P2). Whole-item Replace and Merge exist; nobody has asked for more.
- **In-product analytics.** The privacy policy promises none; measure with store and GitHub numbers instead.

## How PRs merge

Decided by the owner on 2026-10-17. A PR merges only when CodeRabbit has formally approved its final head commit, CI
is green and every review thread is resolved. A commit pushed after an approval needs a fresh `@coderabbitai review`
and a new approval. Code PRs collect on the release branch; before that branch goes to `main`, the release PR gets one
full CodeRabbit pass, which also covers the commits from #30, #33 and #34 that merged before this rule.
